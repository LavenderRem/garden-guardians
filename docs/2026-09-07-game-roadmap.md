# 植物大战僵尸式塔防游戏：最快实现路线与工具调研

调研日期：2026-09-07。状态：供评审的规划草案，尚未进入实现。

本轮只编写规划，没有创建游戏工程、编写程序、生成素材、安装插件或调用付费生成服务。当前工作目录为空，方案按新项目设计。

## 1. 推荐结论与假设

推荐采用 **Phaser 4 + TypeScript + Vite，先完成浏览器单机版，再决定是否打包 Windows**。以“收集资源、放置植物、按行阻挡敌人、抵御波次”的体验为复现目标；角色形象、名称、场景、UI、音乐、音效和视频均自行创作。

暂定假设：

- 桌面 Chrome / Edge 优先，横屏，鼠标操作；触控作为后续适配。
- 先做白天庭院这一种场景，不要求首版覆盖原作全部内容。
- 一名熟悉前端或游戏开发的开发者配合 AI，允许使用在线素材生成服务；账号、额度与预算尚未确认。
- “自己创建素材”理解为允许 AI 生成、自己绘制、自己录制和合成，不使用现成游戏资源包。
- 视频指原创片头及演示视频；战斗中的角色采用精灵动画。

如果最终目标是原生桌面长期开发，Godot 值得改选；如果要求手机应用商店发布，需要先增加触控、打包和真机验证阶段。这些选择尚未锁定。

最快的关键路径：**固定范围 → 最小素材样本 → 一关完整体验 → 批量补素材和内容 → 测试调优 → 发布验证**。不应先生成几十种角色再确定它们在游戏中的尺寸和动作。

## 2. 首版范围

| 项目 | 可玩样板 | 原创素材首版 |
| --- | --- | --- |
| 场景与棋盘 | 1 个庭院，5 行 × 9 列 | 同一场景，复用棋盘 |
| 植物功能 | 产资源、单发攻击、阻挡，共 3 类 | 增加范围爆发，共 4 类 |
| 敌人功能 | 普通、装甲，共 2 类 | 增加快速型，共 3 类 |
| 关卡 | 1 关，约 3–5 分钟 | 3 关，教学、装甲压力、组合挑战 |
| 基础系统 | 资源、种植、冷却、攻击、受伤、胜负、重开 | 增加铲除、每行一次救场装置、暂停、音量、进度保存 |
| 美术 | 同风格的少量原创静态图和简易动画 | 全套原创角色分层、动作、场景、卡牌和反馈特效 |
| 音频 | 原创短音效与一段音乐样本 | 12 个基础音效、2 段配乐、胜负短乐各 1 段 |
| 视频 | 可延后到首版阶段 | 1 段 6–8 秒可跳过片头，1 段 20–30 秒实机演示 |

首版不安排夜晚、泳池、屋顶、迷雾、图鉴、商店、成就、无尽模式、联网、账号、付费系统或关卡编辑器。这些会分别增加规则、美术或服务端工作，影响最快交付。

## 3. 技术路线比较

| 路线 | 适用条件 | 本项目的取舍 |
| --- | --- | --- |
| Phaser 4 + TypeScript + Vite | 浏览器试玩、代码驱动、快速分享 | 推荐；场景、精灵、输入、动画和音频集中在同一游戏框架内，减少自行组装 |
| Godot + GDScript | 原生桌面优先、希望使用完整场景编辑器 | 备选；适合长期做游戏，但需额外验证 Web 导出、音频和部署环境 |
| PixiJS + TypeScript | 已有自己的游戏逻辑层，主要缺渲染 | 本次优先级较低；渲染灵活，但要自己组合更多游戏系统 |

上述优先级是针对本项目的工程判断，不是引擎通用性能排名。Phaser 官方资料确认 Phaser 4 于 2026 年 4 月发布，面向 2D WebGL，支持 JavaScript / TypeScript；执行时应选定并锁住当时稳定的小版本，避免混用 Phaser 3 的渲染插件和示例。[Phaser 4 变更](https://phaser.io/news/2026/05/phaser-3-vs-phaser-4)、[Phaser 4 定位](https://phaser.io/news/2026/07/no-you-didn-t-miss-a-3d-update)

Godot Web 导出需检查其当前平台限制；计划包含 Web 时优先用 GDScript，并以官方稳定文档核对导出路径。[Godot Web 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

PixiJS 官方将自身定位为渲染系统；本项目需要的完整玩法层仍由项目提供。[PixiJS 介绍](https://pixijs.com/8.x/guides/getting-started/intro)

首版直接使用 Phaser 管理游戏 UI，不引入 React / Next.js、数据库、ECS 框架或通用物理引擎。这里只需要按行前进、格子占用和简单命中判定。桌面打包在浏览器首版验收后单独评估，不让打包工具阻塞核心玩法。

## 4. 技术架构

整体数据流：**玩家输入 → 操作校验 → 战斗状态更新 → 战斗事件 → 画面、音效与 UI 反馈**。

| 模块 | 负责什么 | 关键边界 |
| --- | --- | --- |
| 场景管理 | 加载、菜单、战斗、结算 | 切换场景时释放监听、动画、音频及战斗对象 |
| 棋盘与输入 | 屏幕坐标转格子、选卡、放置、铲除 | 资源足够、冷却完成、格子可用后才提交种植 |
| 战斗模型 | 植物、敌人、投射物、血量、位置和状态 | 规则尽量使用普通 TypeScript 数据，不依赖贴图尺寸 |
| 战斗更新 | 产资源、锁定目标、射击、移动、啃食、伤害、死亡 | 采用统一模拟时钟；固定更新步长初定 1/60 秒 |
| 关卡与波次 | 关卡配置、出怪时刻、行选择、胜负 | 波次结束且场上敌人清空才胜利；敌人突破且救场用尽则失败 |
| 表现层 | 精灵、分层动作、粒子、受击和死亡反馈 | 动画反映画面；实际伤害时间由战斗规则决定 |
| 音频管理 | 背景音乐、事件音效、音量和静音 | 用户点击开始后启用；限制同类音效同时播放数量 |
| 本地存档 | 已解锁关卡和设置 | 带版本号的小型 localStorage 数据；不保存首版战斗中途状态 |

植物状态采用待机、动作、死亡；敌人采用移动、啃食、受控、死亡。每类植物和敌人的差异用少量行为与数据配置表达，不提前实现通用技能编辑系统。

碰撞按行筛选，再比较水平位置和碰撞范围；投射物检测上一位置到当前位置的经过区间，避免低帧率时穿过敌人。角色视觉大小、点击范围和战斗碰撞范围分别定义。

暂停或切到后台时停止模拟；恢复时不补算整段离开时间。相同随机种子及相同输入序列应能在规则测试中复现同一战斗结果。

资源服务与游戏运行彻底分开：生成服务只在制作阶段使用，成品只加载导出的图片、音视频与配置。生成服务密钥留在制作环境，游戏不调用这些接口。

建议未来目录职责：

- `src/game/scenes/`：加载、菜单、战斗和结果场景。
- `src/game/battle/`：棋盘、单位、战斗更新和关卡波次。
- `src/game/presentation/`：角色动画、特效、战斗 UI。
- `src/game/audio/`、`src/game/save/`：音频和存档。
- `src/content/`：植物、敌人、关卡和素材映射数据。
- `public/assets/`：实际发行的压缩素材。
- `art-source/`：生成原图、分层源文件、音乐母版、视频源文件。
- `docs/assets/`：素材清单、风格规范、生成记录。
- `tests/`：规则测试与浏览器验收。

这只是职责规划，本轮不创建这些代码目录。为一关写最少系统，第二关再验证数据复用能力。

## 5. 原创图片制作流程

推荐风格：明亮、夸张、轮廓清楚的 2D 手绘卡通；保持庭院塔防的可读性，另设原创轮廓、服饰、表情和配色。

1. 先制作一张整体风格参考，以及一株攻击植物和一个普通敌人的标准立绘。固定视角、描边粗细、光照方向、色板、角色比例。
2. 生成一张不含文字的庭院背景。棋盘线、交互高亮、血条和文字由游戏绘制，确保位置准确且可调整。
3. 以标准立绘为参考生成其他角色；每次只改变需要的部分，避免整批角色出现风格差异。
4. 为每个角色准备可独立摆动的部件，如头、身体、手脚、叶片；必要时人工补绘遮挡下的连接处。
5. 先做一套可用动画并在实际格子大小检查，再批量生产。待机用轻微缩放和旋转，攻击用蓄力、后坐、回弹，移动用身体起伏和四肢摆动。
6. 少数复杂特效使用短帧序列。统一透明边缘、角色脚底锚点、导出尺寸，再打包纹理图集。

首版图片目标：1 张战斗背景、1 张菜单主视觉、4 套植物、3 套敌人、4 张卡牌、约 8 个 UI 图标、约 6 类投射物及特效元素。卡牌优先复用角色图，装甲敌人优先复用身体骨架并增加原创装备部件。

建议规格：工作画布 1280×720；角色原图通常 512×512，实际角色大小按棋盘校准；母版保留透明 PNG，发行采用经透明度验证的图集。单图集先控制在 2048×2048 内，具体数量由装箱与设备验证决定。中文 UI 文本不烘焙到生成图里。

不建议把“AI 一次生成整张连续动作精灵表”作为关键依赖。生成结果可能出现帧数、角色比例和锚点不一致；分层图与少量关键姿态更容易校正。这是制作策略判断，需要用首个样本验证。

图片验收：实际显示尺寸可辨认、透明边缘无白框、脚底位置一致、攻击方向正确、背景与角色对比足够、动作循环无明显跳变。

## 6. 原创视频制作流程

视频用途限制为开场和演示材料，不参与战斗判定。

- 片头：使用已经确认的原创庭院及角色参考图，制作 6–8 秒简单镜头；内容为庭院苏醒、远处敌人出现、植物准备迎战。文字标识在剪辑阶段叠加。
- 演示：首版稳定后录制 20–30 秒真实操作，展示收集资源、放置、射击、敌人受击和胜利，配自制音乐与音效。
- 交付：保留源片，发行优先测试 720p MP4；片头必须可跳过，失败或加载慢时直接进入菜单；不把视频列入战斗首屏必载资源。

首选图生视频，使用 Higgsfield 或 Runway 二选一。Runway 官方 API 支持图生视频；Higgsfield 官方提供图片和视频的插件 / MCP 接入。[Runway API](https://docs.dev.runwayml.com/guides/using-the-api/)、[Higgsfield 接入说明](https://higgsfield.ai/creator-hub/help-center/integrations/how-do-i-connect-higgsfield-to-ai-agent)

如果不使用付费视频生成，仍可用原创分层图片、镜头移动、剪辑和原创配乐合成视频；视频本身依然由项目制作。生成视频失败不应阻塞战斗开发。

视频验收：与游戏角色风格一致、无明显形体突变、无生成乱码、可跳过、不会导致首次进入卡住；演示片呈现实际已实现玩法。

## 7. 原创音频制作流程

首版 12 个基础音效：按钮、种植、收集资源、发射、普通命中、装甲命中、啃食、敌人死亡、范围爆发、波次预警、铲除、救场装置。

配乐：菜单 30–45 秒、战斗 60–90 秒；另做胜利和失败各 3–5 秒短乐。首版无需角色对白。

1. 先定音色：轻松、略带荒诞感、打击反馈清楚；自行确定节奏和乐器组合。
2. 使用 ElevenLabs 生成音效及配乐，或通过自行录音、合成与编曲制作。
3. 每个高频音效生成少量候选，优先解决种植、收集、射击和命中四种反馈；避免在游戏里叠加后过吵。
4. 用音频编辑器裁掉首尾空白、短淡入淡出、对齐主观响度，检查配乐循环接缝。
5. 保存原始质量文件，发行导出经目标浏览器验证的压缩格式；按音乐和音效设置独立音量。

官方能力已核实：ElevenLabs 提供文本音效生成接口和音乐创作接口。某个 MCP 连接是否暴露全部创作工具，必须以授权后的工具清单和小样测试为准，不能将“服务有 API”等同于“当前对话可调用”。[音效 API](https://elevenlabs.io/docs/api-reference/text-to-sound-effects/convert)、[音乐 API](https://elevenlabs.io/docs/api-reference/music/compose)

音频验收：无削波、无突然截断、循环接缝不突兀、重复射击不会淹没其他声音；静音和暂停正确；第一次点击开始后音频可以播放。

## 8. 插件、应用和 MCP 调研

插件是接入包，MCP 是工具连接方式，API / CLI 是其他自动化入口；装更多接入层并不会自动缩短开发时间。优先补齐实际缺失能力。

### 当前已能使用的能力

| 能力 | 本轮确认状态 | 项目用途 |
| --- | --- | --- |
| 内置 ImageGen / imagegen 技能 | 本会话有图片生成工具 | 原创场景、角色、卡牌、参考图；制作阶段调用 |
| Browser / CUA | 本会话有浏览器控制工具 | 试玩、截图、交互检查；Canvas 战斗需结合截图和坐标 |
| GitHub | 本会话有相关连接工具 | 后续代码版本与问题跟踪；具体仓库权限尚未检查 |
| Figma / Pencil | 本会话有设计工具 | 可选的菜单、HUD、风格板；不是首版必要环节 |
| Sites | 本会话有托管工具 | 后续浏览器演示发布候选；需验证项目构建方式和资源限制 |
| Build Web Apps 技能 | 当前技能目录中存在 | 后续前端实现及视觉测试辅助，不代替游戏引擎 |

上述状态来自本轮实际工具和技能列表，不代表已经为此项目完成配置或运行验证。

本轮没有可调用的全目录插件搜索接口，因此采用当前工具列表、用户提供的推荐目录与官方网页交叉查询；以上不是插件市场的穷尽结果。没有安装或授权任何新插件，也没有验证账户区域、套餐或余额。

### 本地制作应用

| 应用 | 作用 | 首版选择 |
| --- | --- | --- |
| Aseprite | 少量帧动画、精灵表和批量导出 | 需要帧动画修整时使用，先确认许可；不是必须购买 |

最小新增组合为 **ElevenLabs + 一个视频服务**。图片用现有 ImageGen，试玩用现有 Browser；Figma、地图编辑器和其他 MCP 不进入关键路径。

## 9. 整体开发流程与验收

以下为范围受控、开发者熟悉技术且账号可用时的工作量估算，不是实测或交付承诺。一个有效工作日按约 6 小时计算；素材反复调整、学习引擎和账户接入等待另算。

| 阶段 | 产出 | 估算工时 | 通过条件 |
| --- | --- | --- | --- |
| 0. 前期设计与制作验证 | 范围、规则表、风格样本、素材清单、工具接入小样 | 3–5 小时 | 一株植物、一个敌人、一条音效和视频路径确认可用 |
| 1. 核心原型 | 可种植、可射击、敌人进攻、胜负、重开 | 8–12 小时 | 一关从开始到胜负可完整运行；规则不依赖精细美术 |
| 2. 可玩样板 | 原创基础画面、3 植物、2 敌人、1 关、关键音效 | 6–10 小时 | 非开发者能理解操作，连续重开没有明显故障 |
| 3. 内容与完整素材 | 4 植物、3 敌人、3 关、全部首版图像与音频、片头 | 12–20 小时 | 素材清单全部落实；新增关卡主要修改数据 |
| 4. 调优、测试与发布 | 性能与交互修复、部署包、实机演示视频 | 8–14 小时 | 通过下列首版验收并在实际发布地址复测 |

总估算约 **37–61 小时，建议安排 7–12 个工作日并留出反馈余量**。可玩样板约 17–27 小时；8–12 小时只能期待核心原型，不等同于全素材成品。若开发者需要学习引擎或追求高质量逐帧动画，需重新估算。

制作安排上，在角色尺寸和素材映射确定后，素材制作与玩法开发可交错推进；批量素材必须等待样本合格。音乐与片头可以稍后接入，不能反过来牵制棋盘规则。

首版验收：

- 种植：资源不足、卡牌冷却、已占用和越界操作均无效；无效操作不扣资源、不启动冷却。
- 战斗：仅命中有效目标；敌人被阻挡时停下啃食；死亡对象不再攻击、产资源或受重复奖励。
- 关卡：预定波次全部刷出且敌人清空才胜利；可稳定触发失败、救场、重开及下一关。
- 时间：不同帧率下射速、资源产出和移动速度一致；暂停与切到后台不会偷偷推进。
- 自动测试：规则层优先覆盖种植扣费、冷却、碰撞、伤害、波次和胜负；用固定随机种子复现场景。
- 浏览器测试：覆盖首次开始、音频解锁、暂停、重开、进度恢复、资源加载；Canvas 内容结合截图、坐标与测试状态断言，不仅依赖 DOM 文本。
- 视觉测试：1366×768 和 1920×1080 桌面视口无遮挡、点击映射正确；手机支持不在此次验收中。
- 性能目标：在后续明确的一台参考电脑上，45 株植物、约 80 个敌人和 150 个投射物压力场景力争 60 FPS，记录帧耗时；此为目标，尚未实测。
- 稳定性：持续运行 15 分钟、重开 10 次，检查异常、事件重复、音频残留与内存持续增长。
- 加载目标：首屏必要资源尽量不超过 15 MB；视频延迟加载。在实际目标网络测首屏时间后决定进一步压缩。
- 素材：图片、音频、视频均有原创源文件或生成记录，无临时占位资源混入发行包。

发布流程为本地构建 → 本地预览生产包 → 浏览器验收 → 选择静态托管并上传 → 实际地址复测 → 保存可回退版本。成品默认是网络 URL 或本地服务器启动的静态构建，不假定双击 HTML 即可运行。

## 10. 成本控制和后续扩展

本轮不购买订阅，不给未经验证的套餐报价。下一阶段先用 1 个角色、1 条音效、1 段配乐和 1 段短视频完成成本与质量测量，再根据实际每次生成消耗制定预算。

素材生成初期每项先取 2–3 个候选；若连续结果不满足风格，调整参考与提示，不通过大量重试堆出成品。优先复用已确认的角色部件和卡牌裁图；保留原始文件，避免重复生成。

每份素材记录：素材 ID、用途、生成工具及模型、提示、参考图、生成日期、原始文件、后处理步骤、导出文件和采用状态；有随机种子时记录。服务条款与素材使用许可在发行前按实际账户核对并留档。

后续扩展顺序建议为更多植物与敌人 → 更多关卡 → 新地形和特殊规则 → 触控适配或 Windows 打包 → 再按需要考虑云存档。每次扩展必须有独立可玩的验收版本。

开始实现前优先确定三件事：首发平台、允许的素材生成预算、偏好的画风。本草案已为未确认项提供默认方案；在用户要求进入下一阶段之前，保持只规划状态。
